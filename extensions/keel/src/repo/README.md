# Keel repository effects

Import from `index.ts`. Persist the discovery snapshot, immutable `RepoOp` and its unique key **before** passing them to `converge(exec, repo, op)`. Retry that plan, not a refreshed snapshot. Use a new key for a new attempt. Expected obstructions, conflicts and proof failures are results; Git and I/O errors are not evidence of success.

## Start and publish

- `readRepo` discovers the shared layout and reads base and trunk. Use short branch names, not `HEAD` or qualified refs. Trunk cannot be `main`, the base, or in keel's namespace. A missing trunk differs from a trunk pinned to a commit. Discover again for new work.
- Use `layout` for branch names and checkout paths. `start_build` and `worktree` create refs with an absent-old-value CAS. Replay recognizes the completed target before comparing the source tip: the pinned creation SHA and name/key-bound creation reflog entry for a branch, plus the locked registration and reciprocal gitdir links for a worktree. An incomplete creation still checks its source. Two starts pinned before trunk existed may share trunk at their pinned base only when its latest reflog entry proves keel created that name. This does not relax the key check on either build. Publishing a worker or advancing a build requires the branch's own creation entry; a replacement at the same hash or another branch's copied log is insufficient. A branch checked out elsewhere (including one reserved by rebase or bisect) isn't available for CAS.
- A stale `start_build` may report `moved` with `keelMoved: true` **only for trunk**: its current reflog and landing parent chain attribute every move from the pinned base to keel. Missing ownership evidence (including older unqualified reflog messages) or a manual ref update is not enough. When re-discovering, compare the new snapshot's trunk to that exact `actual` before planning a new start; don't silently accept a third tip.
- `readPublishable(exec, repo, worker)` requires a clean worker on its owned branch descending from its pinned base. A successful result includes `{sha, base, changedPolicyFiles}`. For review use `git diff base sha`, not the current build tip. The comparison uses the worker/build merge base, so it does not include changes the worker merely merged from the build. If there are multiple best bases, keel combines them in a deterministic comparison commit without advancing a ref. Unreferenced comparison commits have Git's ordinary object retention.
- `changedPolicyFiles` is the sorted list from that same commit comparison, limited to files under `.keel/principles/` and `.keel/playbooks/` (including nested files). Git lists a rename as a deletion and addition, so the report includes each in-scope path. The list informs review; it does not gate publication or merge.

## Integration and proofs

`merge_item` and `take_trunk` construct the candidate before advancing the build. Pin the trunk to take. A conflict returns paths and the opposing commit; it creates no integration checkout. A successful merge/combination returns the commit and check reports. A completed take recognizes its own candidate and receipts even if trunk has since moved.

The **designer writes the proof commands**. Keel runs them as Mandate data, never as tool arguments supplied at merge time. Each `Check` has an `id`, `argv` and a positive integer `timeoutMs`. Commands run against the exact candidate in a disposable, detached integration checkout, with the owner's process environment (including locale and Git config), not the isolation settings for keel's own Git calls. Untracked outputs are ignored. A tracked edit (including a staged change), a different commit, or attachment to a branch fails proof. `checks_failed.sha` is always the **candidate**, never the command's resulting HEAD. `checks` preserves command exit codes and output tails; `changes`, when present, names the paths and whether HEAD changed. A same-tree commit can change HEAD with no paths. If a proof destroys the directory or its gitfile, the checkout no longer resolves to the candidate: `changes` reports `{ paths: [".git"], headChanged: true }` when the original locked registration still proves where to record the result. Attaching to the build also fails, including on receipt replay. A failed proof does not advance the build.

Keep the checkout until the result is durable: immutable per-command receipts prevent rerunning an acknowledged command on a CAS retry. Before rerunning a check without a receipt, keel restores interrupted tracked changes and index state and detaches at the candidate, without resetting an attached branch. A broken checkout without a receipt cannot host a retry and is `occupied`. Checks must be replay-safe; a runner lost between the command and its receipt cannot guarantee exactly-once external effects. The POSIX `nodeExec` bounds captured output and kills remaining members of a proof's process group on timeout or when the command exits, pass or fail. The deadline includes draining stdout and stderr. If an escaped descendant still holds a pipe at the deadline or 250 ms after command exit, keel closes its end and reports exit code 124; it does not chase detached processes. A proof can outlive a **killed runner** and overlap its retry. Keel never signals a PID recalled from disk: it might have been reused. A custom `Exec` must provide the same process handling and replace, not overlay, the Git environment.

## Cleanup

- `checkout` creates a detached verifier. After a pass or supersession, plan `remove` with its original target. Removal requires the registration in this repository, its disposable-checkout lock/key and both gitdir links, not the verifier's current commit or detachment. It may discard edits and unreferenced verifier commits; it never deletes a branch.
- After **any** integration result, plan `remove` with `target: { kind: "checkout", key: integrationOp.key, path: integrationOp.integration }`. No SHA is required. An absent path with no registration is already removed. Only at the canonical integration path for the key, a missing directory's surviving registration can be removed: keel requires a unique worktree registration with the checkout lock/key and an admin directory whose commondir and backlink agree. There is no directory to delete. A **present** directory without its matching gitfile stays `occupied` (it may be a replacement); move it aside manually before retrying cleanup. A missing verifier with a surviving registration, or missing admin ownership evidence, is also `occupied`. Disposable locks are distinct from worker locks: a mistaken checkout target cannot discard a worker. Older verifier/integration locks that do not distinguish these roles are refused, not guessed at.
- Plan worker `remove` with its original `worktree` target. Without `merged: true`, even ignored files keep it. **Only once the caller knows the branch was merged**, set `merged: true` on `remove` to discard ignored outputs. Supply the optional `mergedHead: Sha` from the merge result as well: if the current worker HEAD is not its ancestor, removal returns `kept` with an ancestry reason and `files: []`, leaving the worker intact. Without the SHA, `merged: true` still trusts the caller; the SHA alone does not authorize discarding ignored files. Tracked edits, untracked nonignored files, assume-unchanged/skip-worktree entries and gitlinks still return `kept` with `files`. The outer index cannot certify submodule contents. The worker branch survives removal; per-worktree reflogs and private refs do not.

## Landing

Hold the landing slot. Persist `{ kind: "prepare_landing", key: prepareKey, landing }`, where `landing` pins its own future CAS key, expected trunk, combined commit and message. `prepared.sha` is the exact unreferenced target; persist it. If the tree already equals expected trunk's tree and trunk is still there, `unchanged` ends the landing **without a commit or ref update**. A stale no-change plan reports `moved` instead.

When trunk moved since the full-set pass, have the verifier check **the prepared SHA**, not the unsquashed combined commit, while holding the slot. `converge` then runs `{ ...landing, kind: "land", target }`. Keel is the sole writer of trunk: at old, try one CAS to new; at new, report success without writing; anywhere else, report `moved`. There is no witness ref. Cancellation does not interrupt or undo an in-flight landing.

Commits use a fixed keel identity and the first parent's timestamp in UTC. A landing's only parent is the stored trunk; its tree is the combined commit's tree. A pruned prepared target can be recreated with the same ID while its inputs exist. Ordinary Git object retention still applies.

## Limits

The **caller, not the kernel**, serializes operations that create or advance the same build ref (`start_build`, `merge_item`, `take_trunk`). When trunk does not yet exist, serialize a start that may create it against a landing on that trunk. Landings themselves use the project landing slot. Independent checkout creation and cleanup on distinct paths need no per-build lock; sequence use and removal of the same checkout. Keep repository administrative files and configuration trusted. Ownership checks defend against ordinary foreign checkouts, changed refs and replaced directories, not a malicious process with write access to Git administration. Ref CAS is atomic; inspecting and removing a worktree is not one OS transaction. The crash tests cover either side of completed Git commands, not interruptions inside Git's filesystem operations. Where registration, backlink or ownership evidence is missing, keel refuses rather than repairing by guesswork.

Creation evidence expires with the reflog, so a long-idle build may be refused. Keel isolates Git from global configuration, including global excludes, filters and `safe.directory`; files ignored only by the owner's global config count as dirt at publish.
