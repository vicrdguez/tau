# Keel repository effects

Import from `index.ts`. Persist the discovery snapshot, an immutable operation spec, and its unique key **before** running an effect. Don't refresh its inputs on retry. A new attempt gets a new key. A Git or I/O error is not evidence of success; expected obstructions, conflicts and proof failures are results.

- `readRepo` discovers the shared layout and reads the base and trunk tips. A missing trunk differs from a trunk planned at a particular commit. Discover again when planning new work.
- Use `layout` to name branches, worker/verifier paths and per-effect integration paths. `start_build` and `worktree` create refs with an absent-old-value CAS. Replaying a creation requires both the pinned commit and Git's creation reflog message. The creation message binds the branch name and key. Publishing a worker or advancing a build also requires its creation entry: a replacement branch at the same hash, or a copy with another branch's log, isn't the original. Expired evidence is not permission to reclaim a branch. The configured trunk is different: by contract it is keel's sole-writer ref, and can predate the work. A branch checked out elsewhere (including one reserved by a rebase or bisect) isn't available for CAS.
- Give `readPublishable` the planned worker, not a supplied hash. Omit globs for all changed paths. With globs, matching is Git's top-level glob pathspec syntax and an empty list selects nothing.
- `checkout` materializes a detached verifier. Plan `remove` with its original target after the pass or supersession. A worker is removed only when clean (including ignored files); its branch survives. Git status trusts assume-unchanged and skip-worktree entries, so keel reports these as unverified dirt. It retains workers with gitlinks rather than recursively discarding submodule data that the outer index cannot account for. A dirty verifier may be discarded **only** with its lock, registration, reciprocal gitdir links, detachment and planned commit intact. A missing directory with a surviving registration is occupied, not removed.
- `merge_item` and `take_trunk` construct the result with Git's merge machinery and check the exact detached result before the build CAS. Pin the trunk to take. Keep the integration checkout until the result is durable: it holds per-check receipts. It too can be removed as a detached checkout with its creation key and result SHA.
- Under the lane's landing slot, persist the landing spec and call `prepareLanding`. Persist the returned target. When trunk moved since the full-set pass, verify this **target**, not the unsquashed combined commit. `land` may advance only from the stored old commit to the stored new one. At the new SHA it returns success without writing; everywhere else other than old it reports moved. Cancellation does not interrupt or undo this operation.

Commits use a fixed keel identity and the first parent's timestamp in UTC. Re-creating the object thus gives the same SHA rather than relying on a trailer search. A landing has just the stored trunk as parent and the combined commit's tree. An unreferenced prepared target can be rebuilt from its plan while its inputs exist; ordinary Git object retention still applies.

The caller supplies trusted Mandate commands, not tool arguments. Checks must be replay-safe, run against a clean tree, and leave it clean; use ignored or external storage for build outputs. An acknowledged result isn't repeated on a CAS retry. No process runner can guarantee exactly-once external side effects if it dies between a command and recording its exit. The default POSIX runner bounds proof time and output and replaces the inherited Git environment. A custom `Exec` must honor the same contract; do not pass an adapter that overlays rather than replaces the environment.

The ownership checks defend against ordinary foreign checkouts, changed refs and lost or replaced directories. They are not a sandbox or a lock against a malicious process with write access to Git's administrative files. Git's ref CAS is atomic; a filesystem inspection and a later worktree operation are not one OS transaction. The crash tests inject runner loss on both sides of completed Git commands, not inside Git's filesystem operations. If an interrupted Git process leaves an incomplete registration, missing backlink or dirty checkout, keel stops rather than repairing it on a guess. Serialize effects per build as designed, keep the repository and its administrative configuration trusted, and never infer ownership from a name alone.
